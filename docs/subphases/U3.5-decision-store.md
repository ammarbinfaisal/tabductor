## Scope

Three things: (1) the editor palette gains the **decision** node; (2) a **workflow store
browser** — tables, row counts, the schema per version; (3) a read-only **query console**
running the *same fenced read path* as `store.query`; plus store-schema migration diffs
(additive/destructive) shown at publish. **NOT in scope:** LLM compilation of store schemas
from prose (S8 — this slice authors DDL/table-spec directly, the same "artifact arrives as
data" posture S5g itself specified), a second query path of any kind, touching
`packages/store`/`packages/engine`/`packages/db`/`apps/engine` (S5h's disjoint territory this
round).

## Deliverables

1. **Backend — every datum from a tRPC procedure with a system test:**
   - `store.overview({workflowId})` — the current store-schema version, its description, and
     per-table `{name, primaryKey, columns, rowCount, rowCountError}`.
   - `store.query({workflowId, sql})` — the console. Routes through `@tabductor/store`'s
     `runStoreQuery` *directly*, no client-controlled cap/timeout override. A rejection is
     returned as data (`StoreQueryResult`'s `ok:false` branch), never thrown.
   - `store.previewMigration({workflowId, ddl, tablesSpec})` — `checkDdlShape` +
     `classifyMigration` (both `@tabductor/store`), read-only: no `provision`, no
     `applyMigration`, no `store_schemas` row written.
   - System tests in `tests/system/store-console.test.ts` (new file — S5g's own test files
     untouched): the console rejects a write/DDL/multi-statement/non-existent-table exactly as
     `store.query`'s own fence tests assert; row counts + schema listing correct; an oversized
     result capped at the fence's default with no client-supplied override to widen it.
2. **Editor palette: decision node.** Its visual treatment — a third entity-family token pair,
   argued below, not a raw color.
3. **Store browser + query console UI**: a workflow sub-route, read-only, over the three
   procedures above, plus a schema-diff panel in the (minimal, direct-DDL) publish flow.
4. **Hook policy absolute; Ruled Ink tokens only; no new deps; no UI tests; no `as`-casting.**
5. **Docs**: this file; a U3.5 row on `ROADMAP.md`.

## As built

**Fork point.** The worktree started at `dc4de11` (only through S2b), two commits behind the
`04d7ffd` fork point the task named. `dc4de11` was an ancestor of `04d7ffd`, so
`git merge --ff-only refs/heads/main` caught it up cleanly before anything else — no rebase,
no conflict.

**Deliverable 1 — `apps/web/src/server/routers/store.ts` (new), wired into `router.ts` as
`store`.** All three procedures are thin composition over `@tabductor/store`'s already-fenced,
already-tested primitives; the router adds no query path of its own:

- `overview` calls `getWorkflow` (404 if missing), `latestStoreSchema` +`tablesSpecOf`
  (`@tabductor/store`) for the schema artifact, then — this is the deliberate choice worth
  stating plainly — **one `runStoreQuery(pool, workflowId, 'select count(*) as n from "<table>"', …)`
  per table** for the row count. Row counts are not a second read path bolted beside the
  console; they are the console's own function, called with a system-generated `count(*)`
  instead of an owner-typed `SELECT`. A table whose count the fence would somehow refuse
  reports `rowCountError` instead of a silent zero.
- `query` is `runStoreQuery(ctx.pool, workflowId, input.sql, {metrics: ctx.metrics})` and
  nothing else — no `rowCap`/`statementTimeoutMs` override, because the zod input schema
  (`{workflowId, sql}`) has no field for a client to put one in. **This is the confirmation
  the task asked for verbatim: the console does not call a function "as safe as" `store.query`
  — it calls `store.query`'s own `runStoreQuery`, the exact function the decision node's tool
  (`packages/store/src/tools.ts`'s `createStoreQueryTool`) calls, with a workflow id from a
  URL instead of an agent's tool call.** Same reader role, same `READ ONLY` transaction, same
  pinned `search_path`, same statement timeout, same N+1 row cap, same parse gate. Metrics
  (`store_query_duration_seconds`, `store_sql_rejected_total{reason}`) increment through the
  same injected-meter path S5g wired, via `ctx.metrics` (`metricsNow()`, already plumbed for
  `publishStoreSchema`).
- `previewMigration` restates `publishStoreSchema`'s own validate→classify sequence
  (`packages/engine/src/store-schema.ts`, read but not edited — that file is off-limits this
  round) up to but not including `provision`/`applyMigration`: `checkDdlShape` on the
  candidate DDL, `checkDdlShape` on the previous published version's DDL (looked up via
  `latestStoreSchema`, empty map if none), `classifyMigration` on the pair. A DDL that fails
  `checkDdlShape` throws the same `AppError(STORE_SCHEMA_INVALID, …)` `publishStoreSchema`
  throws for the identical failure, so the preview and the real publish report the same error
  for the same bad input. `storeTableSpecSchema` (the zod restatement of `StoreTableSpec`) was
  exported from `workflow.ts` rather than redeclared, so the wire shape has one source, not
  two that could drift.

  This is the "genuinely new read model" the task anticipated might be needed. It is not a
  `packages/engine` addition (the task's stated preference order: try `apps/web/src/server`
  first) — four lines restating a read-only lookup (`latestStoreSchema` + `checkDdlShape`)
  that `store-schema.ts`'s own unexported `previousDdlTables` already does privately was
  cheaper than widening `packages/engine`'s public surface for a UI slice's preview button,
  and kept this slice inside its stated territory.

  **What preview deliberately does not do:** `validateStoreSchemaArtifact`'s third check —
  "applies cleanly to a scratch schema, rolled back" — needs a live connection and touches the
  database, even if only transactionally and rolled back. Preview stays a pure, fast,
  no-connection call; a DDL that passes `checkDdlShape`'s structural gate but would fail
  Postgres's own acceptance (some type combination the structural check can't enumerate) shows
  a diff here and then fails for real at publish, where the full three-layer validation still
  runs unchanged. The diff panel is advisory, the publish call remains the gate — the same
  division `event-centric-model.md`'s compile report draws between "the editor shows you
  something" and "the deterministic gate decides."

  System tests: `tests/system/store-console.test.ts` (new, 16 tests) — the fence rejection
  corpus (multi-statement, `UPDATE`, `DELETE`, `CREATE TABLE`, `SELECT…INTO`, `FOR UPDATE`)
  each asserted with the *same* `reason` `store-fence.test.ts` asserts on `runStoreQuery`
  directly; a non-existent-table `db_error`; a plain `SELECT` success; **501 rows inserted
  directly, queried with no `LIMIT` in the SQL text and no `limit` field in the request at
  all, still capped at 500 with `truncated: true`** — the "hostile/oversized query capped"
  requirement, proven with a real over-cap result set rather than inferred from the package's
  own unit coverage; an unknown-workflow `NOT_FOUND`; `overview`'s row counts and schema
  version against a seeded row, and its empty-state for a workflow with no store yet;
  `previewMigration`'s additive/destructive classification with the physical
  `schema_version` asserted unchanged after a preview (`currentSchemaVersion`, read but not
  written by preview); an invalid-DDL `BAD_REQUEST`. `afterEach` deprovisions every workflow
  this file provisioned, mirroring S5g's own lesson about cluster-global roles.

## Deviations, argued

1. **The store browser does not poll.** U1.5/U2 established `usePolling` at 2s as the liveness
   idiom for runs, events, and endpoint health — all things that change *out from under* the
   viewer while they watch (a run progressing, a schedule firing). A workflow's store schema
   and row counts do not move on their own between an owner's actions in this same page (a
   query, a publish); they move when a decision/asset node runs elsewhere, which this slice's
   scope does not ask this page to shadow live. `overview` reloads after every `publish`
   (the one action on this page that can change it) and on first mount; nothing here needed a
   `setInterval` making a request nobody's edit caused.
2. **The "publish a store schema" form authors DDL and a table-spec JSON textarea directly,
   not through any friendlier surface.** S5g's own scope note says the store-schema artifact
   "arrives as data" pre-S8; there is no compiler yet to turn prose into DDL. Building a nicer
   authoring surface than "two textareas and a zod boundary" would be designing S8's first
   half from inside a UI slice — explicitly out of scope. The `SchemaRows`-style "no raw JSON"
   display law (`event-panel.tsx`) governs how a *compiled* schema is shown; it does not
   forbid this, because there is no compiler output to render read-only — this is the
   authoring surface for an artifact type that has none yet, the same honest posture the
   e2e test fixtures (`CANDIDATES_VISITED_SPEC`, a literal object) already take.
3. **`previewMigration` skips `validateStoreSchemaArtifact`'s scratch-schema DB check.**
   Argued in the As-built section above — preview trades completeness for staying read-only
   and connection-free; the real publish still runs the full three-layer validation unchanged.
4. **No `store.delete`-adjacent affordance, no per-row edit.** Out of scope per S5g itself
   (`store.delete` deferred, v1) and per this slice's own brief ("Read-only, obviously").
5. **The `/workflows/[id]/store` sub-route, not a global `/store` page.** Unlike
   `cdp_endpoints` (U1.5's `/endpoints` argument — no `workflow_id` column, genuinely
   account-wide), `wfdata_<id>` is *defined* per workflow (graph-compilation-llm §3.2); a
   global store page would need a workflow picker this data doesn't otherwise want, where the
   existing per-workflow tabbar (`workflows/[id]/layout.tsx`) already carries Runs/Events/Share
   for exactly this shape of workflow-scoped surface.
