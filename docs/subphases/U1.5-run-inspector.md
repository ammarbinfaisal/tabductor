## Scope

The debugging surface, deliberately built before the agent exists: a per-run timeline of
navigations, actions, and network entries with policy verdicts; screenshots via `blob_ref`;
resource-limit and disconnect failure detail; an endpoint health panel over `cdp_endpoints`.
Prerequisites S3a (traces, screenshots) and S3b (network observer, endpoint pool) are both
in. NOT in scope: LLM calls / emitted-packet views (U2, gated on S4b — no `kind: "llm"`
trace rows exist yet to render), grants/approvals (U5), asset surfaces (U3).

## Deviations, argued

1. **Run detail needed no backend change.** `run.get` (S2c) already returns
   `{run, task, trigger}` — status, `modeUsed`, `attempt`, `startedAt`/`endedAt`, `error`,
   and the trigger event. The prompt anticipated "extend minimally"; the minimal extension
   turned out to be none. `workflowId` is not in the payload because the inspector route
   already carries it as a path param — adding it to the procedure would be a second copy of
   data the caller already has.

2. **Navigation rows render a static "allowed."** `trace_entries.kind = 'navigation'` is
   written only on an *allowed* navigation (`session.ts`'s `onNavigationRequest`); a denied
   one is written as `kind: 'policy_denied'` instead, with `check: 'navigation'`. There is no
   verdict field on a `navigation` row to display because the row's existence already is the
   verdict. The timeline shows both kinds, so the information the spec asked for ("verdict")
   is present — split across two row kinds rather than folded into one field.

3. **The endpoint panel landed on its own page, `/endpoints`, not a workflow sidebar.**
   `cdp_endpoints` carries no `workflow_id` — one CDP connection is a property of the user's
   account (§8), shared across every workflow that happens to use it. A workflow-scoped
   sidebar would either show the same global list on every workflow page (redundant, and
   implies a scoping that does not exist) or need a filter the schema cannot express.
   `JOURNEY.md`'s IA is hub-and-spoke *per workflow*, with a small set of global,
   workflow-independent surfaces above that hub (today: `/workflows`, `/status`);
   `/endpoints` joins that set, one more item in the top nav, following the same shape as
   `/status` (a global, account-wide, non-workflow-scoped page) rather than inventing a new
   pattern.

4. **`HealthStamp` uses the entity-family tokens (ink-blue/amber), not the run-status ramp.**
   `--status-succeeded`/`--status-failed` exist and were the obvious first reach, but they
   name run *outcomes* — reusing that vocabulary for live infrastructure state would make
   "this task succeeded" and "this endpoint is up" look like the same kind of fact when they
   answer different questions. Ink-blue (calm, "in service") and amber (the product's
   attention-drawing "actor" ink) read as a distinct category at a glance, which is the
   point.

5. **No automated test for the blob route itself.** `apps/web/src/server/db.ts` and the new
   `server/blob-store.ts` construct their `Db`/`BlobStore` from `loadConfig()` against the
   real environment (memoized on `globalThis`), exactly like the existing tRPC HTTP route
   (`app/api/trpc/[trpc]/route.ts`) — and that route has no direct test either; S2c's own doc
   permits this ("createCaller coverage is acceptable, note it"). The route's only real logic
   — the `artifacts` lookup, the MIME allowlist, the header set — is thin composition over
   two already-tested primitives: `packages/browser/src/blob-store.ts` (`tests/system/blob-store.test.ts`,
   S3a) and the `artifacts` table (`tests/system/trace-recorder.test.ts`). Verified instead by
   `next build` succeeding with the subpath wired in, and by reading the route against §16
   Threat 15's checklist line by line. A future subphase that gives route handlers their own
   test harness should add one here.

6. **The failure-detail lookup only sees loaded pages.** `findFailureDetail` scans the trace
   entries currently in the client store, which is however many pages "Load more" has
   fetched. For the failure kinds this feature targets (`resource_limit_exceeded`,
   `browser.disconnected`), the triggering action is almost always near the end of a short
   trace and lands on the first page; a run with a very long trace before the failure would
   need one "Load more" click first. The header says so explicitly rather than showing
   nothing.
